# Private relationship and role assertions — partial AM-05.01

The existing Knowledge API now accepts value.type relationship, with relationshipType role_assertion or association, a bounded literal label, exact from entity ref and to entity/event ref, nullable time bounds, explicit limitations, and separate null assessment/proceduralPosture/editorialApproval fields. Relationship IDs/revisions follow the same immutable containing history, expected current logical revision, exact predecessor and private defaults as entities/events/claims. Distinct endpoints must exist in scope. New assertions must deliberately select current endpoint editions; historical records keep their exact older links after entities/events change. Direct relationship-to-relationship references are denied, so these records cannot introduce dependency cycles. No entity identity merge or ID rewrite is performed.

These are research assertions, not proof a person held a role, attended an event, controlled an organization or caused anything. Literal label/relationshipType do not classify guilt, liability, credibility or permission. A snapshot/hash/request ID does not establish identity, provenance or authentication. Context roles/scope/time and supplied state remain TRUSTED HOST INPUT. Current Identity/resource/purpose/consent/rights/source gates, independently qualified evidence and semantic verification remain pending. The API performs no model inference/extraction/provider call. Unknown dates stay null; existing exact UTC/calendar/order validation applies. A known time interval need not be invented or inferred from an endpoint event's date.

Claims may explicitly select an exact current relationship edition in subjectRefs, alongside entities/events. New claim revisions must select current subject editions; old claims preserve their old relationship references. This is a subject dependency, NOT a citation or evidence support. Existing claim-only Evidence-link APIs remain unchanged and require separate exact validated source selectors. Relationship revisions do not automatically rewrite claims, invalidate decisions or imply corrections are complete; downstream correction impact still needs implementation.
